# 決定事項

| ID | 決定 | 理由 |
|---|---|---|
| G-1 | コインは**残高を持たず台帳（追記のみ）で表す**。`available = earned - used` は毎回導出する | 本番 DB にトランザクションが無い（ADR 0001）。残高カラムは更新競合が即バグになる |
| G-2 | `earned` はビンゴの成立ライン数から**その場で計算**し保存しない | ライン数は単調非減少。保存しなければ「ズレた残高」という状態が存在しない |
| G-3 | 換算規則（1ライン何枚・上限・ボーナス）は**イベント単位の設定テーブル**に置く | 当日「足りない／余る」と分かったときデプロイなしで運営が直せる |
| G-4 | 換算は純関数 `calcCoinsEarned(lines, settings)` として `src/lib/gacha/coins.ts` に置く | 依存の向きを守る。DB 無しでテストできる |
| G-5 | 消費は**クライアント生成の冪等キー**を必須とし、1操作＝1キー | 二重タップと通信リトライの両方を同じ仕組みで防ぐ |
| G-6 | 消費 SQL は `HAVING COUNT(*) < ?` 付きの**単一 INSERT ... SELECT** | 1リクエスト＝1SQL の制約下で、残高超過を SQL 自身に判定させる |
| G-7 | 景品と当選確率は**アプリで管理しない** | 実物のガチャポン筐体を回す運用。確率はアプリの外にある |
| G-8 | 「準備中／公開」は**サーバーの状態**（`gacha_settings.is_enabled`）で持つ | 当日ガチャを止める判断を運営画面からできるようにする |
| G-9 | コイン消費に **socket 通知を出さない** | 個人の消費であり他者に共有する情報が無い。1インスタンス制約（ADR 0002）の負荷も増やさない |
| G-10 | **スタッフの立会いは無い。操作はアプリ内で完結する**（2026-08-27 確定） | 当日スタッフをガチャに常駐させない。立会いを前提にした画面・API を作らない |
| G-11 | 換算は **1ライン = 1枚・上限 4枚**（2026-08-27 確定） | 去年の Flask 実装と同じ。4x4 全10ラインでも 4 枚で頭打ち |
| G-12 | 立会いが無いぶん、**誤操作の防止をアプリ側で厚くする**（確認1段・押下即 disabled・完了画面に消費内容を明示） | 人間の目視確認が無くなるため、取り消せない操作の手前を UI で守るしかない |

## 用語

| 語 | 意味 |
|---|---|
| **獲得枚数 earned** | 成立ライン数から換算した、そのユーザーが得た累計枚数。導出値 |
| **使用枚数 used** | `gacha_coin_uses` の行数 |
| **所持枚数 available** | `max(0, earned - used)`。UI に出るのはこれ |
| **coin_index** | そのユーザーの何枚目か。0 起点。台帳のユニークキーの一部 |
| **冪等キー** | 「使用する」ボタン1押下につき1個生成する UUID。再送でも同じ値を送る |

## G-10 の帰結（何を作らないか）

- スタッフ PIN 入力画面を**作らない**
- スタッフ端末の QR 発行・読み取りを**作らない**
- `gacha_coin_uses` に `verified_by` 列を**作らない**
- 完了画面はスタッフに見せるためではなく、**参加者自身の確認のため**に出す
