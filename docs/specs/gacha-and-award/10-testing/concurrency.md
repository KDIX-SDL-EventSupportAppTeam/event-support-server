# 多重消費を殺す結合テスト（最重要）

ローカル MySQL（docker compose）に対して実行する。
**このファイルのテストが全部通るまで、ガチャを本番に出さない。**

## セットアップ

ユーザー1名・イベント1件・`gacha_settings` を明示投入し、
ビンゴのセルを直接 UPDATE して `lines` を作る（推薦もチェックインも経由しない）。

```
ヘルパー: seedLines(eventId, userId, lines)  … 指定ライン数になるまで is_achieved = 1 にする
ヘルパー: useCoin(eventId, token, key)       … POST /gacha/coins/use
```

## C-1. 同じ冪等キーの並行2回

```
Promise.all([useCoin(k), useCoin(k)])
```

- [ ] 両方が `200` を返す
- [ ] `gacha_coin_uses` の行が **1行だけ**
- [ ] 両応答の `coin_index` が同じ値
- [ ] 両応答の `used` が同じ値
- [ ] `used_at` が同じ（同じ行を見ている）

## C-2. 同じ冪等キーの逐次2回（リトライ相当）

- [ ] 2回目も `200`
- [ ] 行は1行のまま、`used` は増えない

## C-3. 別キーの並行2回・残高1枚

`earned = 1` の状態で異なるキー2本を同時に投げる。

- [ ] **成功はちょうど1本**
- [ ] もう1本は `409 NO_COINS_AVAILABLE`（または再試行の末に `409`）
- [ ] 行は1行、`coin_index = 0`
- [ ] **500 が返らない**（プロキシがユニーク違反を潰しても、手順4の再判定で吸収されること）

## C-4. 別キーの並行5回・残高3枚

- [ ] 成功ちょうど3本、`409` が2本
- [ ] `coin_index` が 0,1,2 で**重複も欠番も無い**
- [ ] `used = 3`、`available = 0`

## C-5. 残高ゼロ

- [ ] `earned = 0` で `409`、行は0のまま
- [ ] `earned = used` の状態で `409`

## C-6. 消費中にライン数が増える

`useCoin` の直前に `seedLines` でラインを増やす／直後に増やす、の両順序。

- [ ] どちらの順序でも `used <= earned` が保たれる
- [ ] 古い `earned` を読んでいても**過剰消費にならない**

## C-7. 別ユーザー・別イベントの独立

- [ ] ユーザーA の消費がユーザーB の `available` に影響しない
- [ ] 同一ユーザーでもイベントが違えば `coin_index` は別系列（0 から始まる）
- [ ] 同じ冪等キーを別イベントで使っても両方成立する

## C-8. 無効化

- [ ] `is_enabled = 0` で使用が `403 GACHA_DISABLED`、行は増えない
- [ ] `is_enabled = 0` でも GET は `200` を返す
- [ ] 消費の途中で運営が無効化しても、成立済みの行は消えない

## C-9. 設定変更との組み合わせ

- [ ] `max_coins` を消費後に下げ、`used > earned` になっても `available = 0` で `200`（例外にしない）
- [ ] その状態で使用すると `409`
- [ ] `bonus_coins` を +1 すると、その場で `available` が1増える

## C-10. 入力

- [ ] `idempotency_key` 欠落で `400`、行は増えない
- [ ] UUID 形式でない文字列で `400`
- [ ] 他イベントの `event_id` を指定すると既存の `requireEventMatchesJwt` で弾かれる
- [ ] 未認証で `401`

## 「起きてはいけないこと」

- [ ] **どのケースでも `used > earned` になる行が生まれない**
- [ ] `coin_index` が重複した行が存在しない（テスト終了時に SQL で全走査して確認）
- [ ] 台帳に UPDATE / DELETE が発行されていない
- [ ] 消費 API が socket を送っていない（G-9）
