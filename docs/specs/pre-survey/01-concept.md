# 背景と設計判断

## 背景

1. 事前アンケートは**イベント開催日の前日まで**に回答してもらう。回答は
   事前推薦マスの材料と、ラフ集合分析の条件属性になる
2. 一方、**アプリ本体は開催直前まで開けたくない。** 完了画面の「アプリに移動する」ボタンは、
   開催直前まで押せない状態にしておきたい
3. 開放の判断は**主催者（organizer = 最高権限者）**が行う。運用上は
   「開催30分前に自動で開く」（タイマー）と「今すぐ開ける／閉じる」（手動）の両方が要る。
   当日の遅延・トラブルで前倒し／後ろ倒しが起きるため、**タイマーを手動で上書きできる**ことが必須

## 用語

| 日本語 | コード上の名前 | 定義 |
|---|---|---|
| 事前アンケート | `pre_survey` | イベント開催前に参加者が回答するアンケート |
| 事前アンケート締切 | `pre_survey_closes_at` | 回答受付終了日時。既定は開催日の前日 23:59 |
| アプリ公開ゲート | `app_access` | 参加者がアプリ本体を使い始められるかを制御する、イベント単位のスイッチ |
| ゲートモード | `app_access.mode` | `closed` / `scheduled` / `open` の3値 |
| 開放予定時刻 | `app_opens_at` | `scheduled` のときアプリが自動で開く日時 |
| 実効開放状態 | `is_open` | 今アプリを開けるかの真偽値。**サーバーが唯一の判定者** |

## 設計判断

### P-1 サインアップ／サインインは既存の参加者認証をそのまま使う

`POST /auth/register` / `POST /auth/login`、`users` テーブル、`role='participant'`。
参加者アカウントを二重に持たせない。回答を `user_id` で一意に紐づけられる。

### P-2 回答は既存の `survey_questions` / `user_survey_answers` に保存する

新テーブルを作らない。分析側（`event-support-analytics`）の読み取り先を増やさない。

### P-3 ログインの可否とアプリ公開ゲートは分離する

事前アンケート期間中もログイン自体は可能で、ゲートは「アプリ本体の画面に入れるか」だけを制御する。
アンケート回答にはログインが必要（P-1）なので、認証を止めると回答できない。

### P-4 実効開放状態はサーバーが算出して返す

クライアントの時計で判定しない。端末時計のずれ・改変で早期入場されるのを防ぐ。
レスポンスには `server_time` を必ず含め、クライアントは時計ずれの補正に使う。

```
is_open =
  mode === 'open'      → true
  mode === 'closed'    → false
  mode === 'scheduled' → app_opens_at !== null && now >= app_opens_at
                         && (app_closes_at === null || now < app_closes_at)
```

### P-5 ゲート状態はイベント単位（`event_app_access` テーブル、events と 1:1）

イベントごとに開催時刻が違う。`events` への列追加ではなく別テーブルにして、
将来の拡張（区画別開放など）に備える。

### P-6 ゲートの書き込みは `organizer` のみ

「運営の最高権限者が切り替える」という要件。運営スタッフの誤操作で早期公開されない。

### P-7 `scheduled` は保存時刻とサーバー現在時刻の比較で判定する。cron を使わない

単一インスタンス運用（[ADR 0002](../../decisions/adrs/0002-cloud-run-single-instance-for-websocket.md)）で
スケジューラを持たずに済む。時刻変更が即座に反映される。

### P-8 手動上書きはモードの変更で表現する

`open` / `closed` に変更することが手動上書き。`scheduled` に戻せば予約が復活する。
状態が3モードに閉じ、UI と監査ログが単純になる。

### P-9 フロントはゲート状態をポーリングする（30秒間隔）

残り時間はローカルで秒カウントする。WebSocket は使わない。
未ログイン〜ログイン直後の画面でも動く必要があり、socket は JWT 必須で `/thanks` に向かない。

### P-10 「関心分野」の選択肢は `categories` から動的生成する

**ビンゴ側の [D-13](../bingo-dynamic-unlock/01-concept/decisions.md) と対の判断。**

アンケートの関心分野とブースのジャンルが別々に定義されていると、突き合わせができない。
**同じ器（`categories`）を使う。**

- 設問 `interest_categories` の選択肢は、`categories` テーブルから生成する
- 回答は `custom_answers` に `category_id` の配列として保存する
- 運営がカテゴリを編集すれば、アンケートの選択肢も変わる
- **編集権限は現状どおり `manager`**（カテゴリ管理画面）
- 他イベントへの汎用化にも効く（分野名をハードコードしない）

> **アンケート締切後にカテゴリを編集すると、既存回答の `category_id` が
> 存在しないものを指す可能性がある。** 分析時に落とせるよう、
> `interest_match` は推薦時点の値を凍結して保存する
> （[serendipity-data.md](../bingo-dynamic-unlock/07-research-logging/serendipity-data.md)）。

### P-11 設問はサーバーから配信する

現在はフロントの `config/questions.ts` にハードコードされている。
P-10 のために動的生成が必要なので、**サーバー配信へ移行する。**
`survey_questions` テーブルに登録し、運営画面から編集できる状態にする。
