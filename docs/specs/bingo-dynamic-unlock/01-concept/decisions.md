# 設計判断

**実装は本ファイルを正とする。** 経緯は
[decisions/meetings/2026-08-20](../../../decisions/meetings/2026-08-20-bingo-spec-change.md) にある。

---

## D-1 参加ボーナスマスは作らない

旧仕様では中央4マスのうち1マスを「参加ありがとう」として最初から**達成済み**で配っていた。これを廃止する。

理由（須藤先生の指摘）:

- 参考にした先行研究はゴールが明確な「山登り型」のタスクで、本ビンゴのオープンなタスクとは性質が違う
- 16マス中1マスを開けても「なぜここだけ開いているか」の説明が難しく、段階的目標としての意味が薄い
- 4マス中1マスが最初から開いていても「3が4になっただけ」でハードルはほとんど下がらない
- **去年のデータとの比較が公平でなくなる**

## D-2 position 5 は「事前推薦マス」として、中身を見せた未訪問状態で配る

完全な自由（真っ白な16マス）は最初の1歩を踏み出しにくいという指摘は妥当である。
そこで中央の1マスに、事前アンケートから推測した推薦ブースを**表示した状態**で配る。

- **達成済みにはしない。** そのブースを訪問して初めて達成になる
- 中央4マスはすべて実訪問で埋まる。旧 D-11（ボーナスブース訪問で中央が埋まらない問題）は消滅する
- 事前アンケート未回答なら `booth_id` は `NULL` のまま。中央4マス全部が自由枠になる
- 推薦の中身は「ベタな推薦」でよい。興味カテゴリと一致するブースから選ぶ

## D-3 解放は「中央マスが2つ揃うたび」に、そのペアが成す1本のビンゴ列に対して起きる

中央4マスから2つを選ぶ組は6通りあり、それぞれが1本のビンゴ列に対応する。
各列の外周マスはちょうど2マスで、6組 × 2マス = **外周12マス**。過不足がない。

対応表は [03-card-lifecycle/unlock-pairs.md](../03-card-lifecycle/unlock-pairs.md)。

**解放イベントは1枚のカードにつき最大3回。**

| 中央の達成数 | 成立ペア数 | 新規ペア | 開放マス数 |
|---|---|---|---|
| 2 | 1 | 1 | 2 |
| 3 | 3 | 2 | 4 |
| 4 | 6 | 3 | 6 |

3マス目が埋まると同時に2組が成立する点に注意する（6回ではなく3回である）。

外周マスが埋まっても解放は起きない。解放の起点は中央マスだけである。

## D-4 最初のビンゴまでのコストは去年と同じ4件に保つ

中央2マス（自由訪問）→ その列の外周2マスが開放 → 外周2マスを訪問、で**4件目にビンゴ1本**が成立する。
去年も「4マス揃えばビンゴ1本」だったのでコストは変わらない。

むしろ最初の2件が完全に自由な分、参加者にとっては易しい。
**ガチャコイン獲得の初期コストを上げないことが段階解放の狙いの一つ**であり、これを満たしている。

## D-5 ビンゴはガチャコインに依存しない（依存は一方向）

ビンゴ側が計算するのは**成立ライン数まで**とする。ライン数をコイン枚数へ換算するのはガチャ側の責務。

- `calcCoinsEarned()` をビンゴのライブラリから外す
- ビンゴカード API は `coins` を返さず `lines_completed` を返す
- ガチャは後から追加する。**その際にビンゴ側を変更しなくてよい状態にしておく**

## D-6 推薦理由文は表示しない。ただしデータとしては残す

理由の説明文はユーザーが読まない可能性が高く、ビンゴの形式自体が
「次にどう行動すればよいか」を直感的に伝えられるため不要（須藤先生の判断）。

- マスに表示するのは**ブース名とブース説明**まで
- 理由の JSON は記録し続ける（研究・デバッグ用）。API では返さない

## D-7 評価は中央なしの星4段階、コメント欄つき、ボタンは「完了」1つ

5段階は中間（3）に集中しやすく、実験データとして分析しづらい。
2ボタン構成（評価を送信 / コメント送信）は、どちらをスキップしたか区別できず UX としても冗長。

- `RATING_SCALE` の既定を **4** に変更する
- 既存の `booth_ratings.scale` にその時点の段階数を保存する運用は維持する

## D-8 カードの段階を保存しない。マスの状態から導出する

「今どの段階か」を `bingo_cards` に持つと、保存された段階と実際のマスの状態が食い違う事故が起きる。

- カードの現在の姿は **`bingo_cells` から導出する**
- 解放の履歴は追記専用の `card_unlock_events` に積む
- `bingo_cards.status` の2値 ENUM は廃止する

## D-9 マスの状態を2つの軸に分解する

旧仕様の `state ENUM('LOCKED','EMPTY','ACHIEVED')` は 2つの軸が混ざっていた。

| 旧 | 見えるか | 達成か |
|---|---|---|
| `LOCKED` | 見えない | 未達成 |
| `EMPTY` | 見える（が中身は空） | 未達成 |
| `ACHIEVED` | 見える | 達成 |

新仕様では「中身が見えているが未訪問」（事前推薦マス・解放後の推薦マス）が主役になるため、
この混在が破綻する。**`is_revealed` と `is_achieved` の2列に分ける。**

## D-10 推薦度は、推薦のたびに全候補ぶんを保存する

`cell_assignment_logs.score` は「マスに載ったブース」のスコアしか残らない。
研究では**推薦されなかった候補が何点だったか**が比較対象になる。

- 解放のたびに、除外されていない全ブースについてスコアを記録する
- 参加者1人あたり 3回 × 約40ブース = 約120行。250人で3万行。DB 負荷として問題ない
- **取らなかったデータは後から取れない。** イベントは年1回しかない

## D-11 `recommendations` テーブルは廃止する

旧「推薦欄」方式のためのテーブル。1推薦につき1行で候補を JSON 配列に持つ構造は、
SQL で展開できず、スコアも評価も残らないため研究に使えない。D-10 の新テーブルが上位互換である。

- テーブルを DROP する
- **既存データも DELETE する**（マイグレーションで明示的に消す）
- `/events/:event_id/recommendations` と `/select` のエンドポイントも削除する
- フロントの推薦欄 UI（`CheckInRecommendView`）も削除する

## D-12 条件属性に `knowledge_level` と `duration_band` を使わない

出展者が自己申告しづらく、評価しづらいデータであるため扱わない（2026-08-24 判断）。
条件属性が不足する場合は、年代・性別など参加者属性の投入を検討する。

**属性の構成は後から変更する前提**とし、推薦エンジン側の1モジュールに閉じ込める
（[05-recommender/contract.md](../05-recommender/contract.md)）。

## D-13 事前アンケートの「関心分野」は `categories` から動的生成する

関心分野の選択肢とブースのジャンルが別々に定義されていると突き合わせができない。
**同じ器（`categories`）を使う。**

- 運営がカテゴリを編集すれば、アンケートの選択肢も変わる
- 編集権限は現状どおり `manager`
- 詳細は [pre-survey](../../pre-survey/README.md) 側の仕様

## D-14 主キーは CHAR(36) UUID（既存踏襲）

既存スキーマはすべて `CHAR(36) PRIMARY KEY` の UUID で、アプリ側が `randomUUID()` で採番する。
新規テーブルもこれに揃える。

## D-15 排他は条件付き UPDATE の `affectedRows` で行う

本番の DB アクセスは HTTP プロキシ経由で 1リクエスト = 1SQL。トランザクションも行ロックもない。
`SELECT ... FOR UPDATE` は使えない。詳細は [rules/coding.md](../../../rules/coding.md) と
[ADR 0001](../../../decisions/adrs/0001-sakura-proxy-error-masking.md)。

解放が最大3回起きるため、**排他の単位も「ペアごと」に3組ぶん必要**になる。

## D-16 解放後のカード外訪問がビンゴに寄与しない問題は許容する

外周マスが確定した後、カードにないブースへの訪問はビンゴに寄与しない。
ビンゴゲームという制約がある以上やむを得ない。**既知のトレードオフとして記録する。**

ただしカード外訪問も**ログとしては必ず記録する**（`check_ins.cell_id = NULL`）。
学習データ・研究データ（推薦なしでの自発訪問＝対照群）として必要である。

## D-17 カード外訪問でも評価は同じように求める

ビンゴには寄与しないが、推薦アルゴリズムの学習データとして必要。
評価収集の分岐にカード内外の条件を入れない。

## D-18 クールタイムは既定 0 秒（機構は残す）

同一ブースへの連続チェックインは `check_ins` の `UNIQUE (user_id, booth_id)` で構造的に防がれている。
去年の 180 秒運用は間隔中央値の下限として効いており、**行動データを歪めていた**（飽和24.2%）。

`CHECKIN_COOLDOWN_SEC` の既定を `0`（無効）とし、0 のときは判定処理自体をスキップする。
