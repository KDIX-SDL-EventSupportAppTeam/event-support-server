# テスト戦略

須藤先生から「ダイナミックな動的レコメンドへの変更は大掛かりな改修になるため、
テストを含め慎重に進める必要がある」との指摘を受けている。**テストは後付けできない。**

| ファイル | 内容 |
|---|---|
| [acceptance-criteria.md](acceptance-criteria.md) | 合格基準チェックリスト |
| [unit-coverage.md](unit-coverage.md) | 純関数で網羅する組み合わせ |
| [rehearsal-plan.md](rehearsal-plan.md) | 実機リハーサルの手順書 |

## 3つの層

| 層 | 何を守るか | 手段 | 実行 |
|---|---|---|---|
| **1. 純関数の単体テスト** | 段階解放のロジックそのもの | Vitest。DB も通信も使わない | 自動・毎回 |
| **2. API の結合テスト** | DB を含めた一連の流れ | Vitest + ローカル MySQL（docker compose） | 自動・毎回 |
| **3. 実機リハーサル** | 人間が触ったときに壊れないか | 手順書 + 人力 | 手動・節目ごと |

## テストしやすい設計にする（実装制約）

**段階解放のロジックを、DB にも通信にも触れない純関数として切り出す。**

```
centerAchieved: Set<number>, unlockedPairs: Set<string>
        ↓ 純関数
newlyCompletedPairs: Pair[]   （各 Pair は line_index と released_positions を持つ）
```

こうすれば中央マスの埋まり順を総当たりでテストできる。
DB 保存・推薦呼び出し・socket 通知は、この関数の外側に置く。

**あとから分離するのは非常に大変であり、最初から分けるしかない。**

## 自動化しないと決めたもの

時間対効果が悪いため、実機リハーサルで確認する。

- QR コードの読み取り（カメラが必要）
- 画面の見た目・レイアウト
- WebSocket 通知の到達（実機の電波状況に依存する）
- 解放演出のアニメーション

## 必ず自動化するもの

- 段階解放ロジック（埋まり順の総当たり）
- 解放の冪等性
- 推薦サービス障害時のフォールバック
- **カード取得 API が「見えないマスの中身」を絶対に返さないこと**
- フェーズ切替の境界値
