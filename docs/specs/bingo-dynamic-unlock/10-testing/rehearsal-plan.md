机上のテストでは絶対に見つからない問題（電波、画面の見づらさ、想定外の操作順序）を潰す。

## 事前に用意するもの

- リハーサル専用のイベント（`POST /organizer/events` で作成）
- ブース10件と QR コード（印刷して貼る）
- 参加者アカウント10件、または各自でその場で登録してもらう
- 事前アンケートに回答してもらう（**本番と同じ導線で**）

## 当日の観察項目

### 必ず確認する

- [ ] 事前アンケートに回答してアプリに入れるか
- [ ] 事前推薦マス（position 5）にブースが表示されているか
- [ ] 2件目のチェックインで**解放演出が出る**か
- [ ] 3件目で**もう一度**解放演出が出るか（1回きりになっていないか）
- [ ] 4件目で3回目の解放が起き、外周12マスすべてが見えるか
- [ ] 開放されたマスが [unlock-pairs.md](../03-card-lifecycle/unlock-pairs.md) の表どおりか
- [ ] 4件目の訪問でビンゴが1本成立するか
- [ ] 評価モーダルが次のチェックイン時に出るか。星4段階とコメント欄と完了ボタン1つか
- [ ] **見えないマスの中身が見えていないか**（開発者ツールで API レスポンスも確認）
- [ ] アプリを閉じて再度開いても状態が保たれているか

### 計測する

- [ ] チェックインから画面が返るまでの体感時間（2秒以内か）
- [ ] 評価回収率（10人×数件でどれだけ集まるか）
- [ ] 解放通知（socket）の到達率。**スマホをポケットに入れた状態でも試す**

### 意図的に壊す

- [ ] 機内モードにしてチェックイン → 復帰後の挙動
- [ ] 同じ QR を2回読む → 409 になり、画面が壊れない
- [ ] 推薦エンジンを止めた状態でチェックイン → フォールバックで解放される
- [ ] 全員でほぼ同時にチェックインする → 解放が重複しない

## 負荷試験（リハーサルとは別に実施）

本番のピークは **1分あたり9.3チェックイン・同時滞在89名**。
その**3倍（1分あたり30件）**を目標に負荷をかけ、以下を測る。

- 解放1回あたりの所要時間
- 解放1回あたりの SQL 往復回数
- 同時 WebSocket 接続数と通知の到達率
- Cloud Run 1インスタンスで捌けるかどうか

**測定して初めて「1台で足りる / 足りない」を判断する。**
足りない場合は socket.io のアダプタ方式（Redis / Cloud Pub/Sub）＋セッションアフィニティを
導入する（半日程度の作業）。予備日程として確保しておく。

> スケールアウトしても**さくら DB への通信往復は減らない**。
> まず SQL 往復回数を減らすことが先である。
