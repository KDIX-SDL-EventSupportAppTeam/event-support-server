# 純関数で網羅する組み合わせ

## 中央マスの埋まり順

中央マスは {5, 6, 9, 10} の4つ。埋まる順序は最大 **4! = 24通り**。
さらに「4つすべて埋まらずに終わる」場合もあるため、
**長さ0〜4のすべての順列（1 + 4 + 12 + 24 + 24 = 65通り）**を総当たりする。

各ケースで検証すること:

- 各段階で新たに成立するペアが正しい
- 開放されるマスが [unlock-pairs.md](../03-card-lifecycle/unlock-pairs.md) の表と一致する
- **同じペアが二度成立しない**
- 長さ4のケースで、開放マスの合計が必ず12マス・重複なし
- 長さ2のケースで開放が2マス、長さ3で6マス（累計）

```
中央達成数 → 累計開放マス数
0 → 0    1 → 0    2 → 2    3 → 6    4 → 12
```

## 「起きてはいけないこと」

**人間は「起きるべきこと」しかテストしない。以下を明示的に書く。**

- 中央2マス達成時、**対応しない外周10マスが開放されていない**
- 外周マスの達成では**解放が一切起きない**
- ペアに含まれない中央マスの組み合わせ（例: 存在しない `pair_key`）が生成されない
- 開放マスに中央マスが含まれない
- 同じ外周 position が2つのペアから開放されない

## ライン判定

- 中央4マスすべて達成でライン数 **0**
- 中央2 + 同一ラインの外周2 で **1**
- 16マスすべて達成で **10**
- 達成した順序に依存しない（集合だけで決まる）

## フェーズ切替の境界

| 決定表の件数 | 期待するフェーズ |
|---|---|
| 0 | COVERAGE |
| 29 | COVERAGE |
| 30 | SIMILARITY |
| 179 | SIMILARITY |
| 180 | DRSA |

しきい値を設定値で変更でき、変更が反映されること。

## 結合テスト（DB あり）

- 中央2マス目のチェックインで、DB の外周2マスに `booth_id` が入り `is_revealed = 1` になる
- 中央3マス目で4マス、4マス目で6マスが開放される
- 同じペアで解放処理を並行に2回走らせても `card_unlock_events` は1行だけ
- `recommendation_scores` に候補全件が入り、`was_assigned = 1` の件数が開放マス数と一致する
- 推薦サービスを 500 / タイムアウトにしても解放が成功する
- **カード取得 API が `is_revealed = false` のマスの `booth` を `null` で返す**
- 解放イベントだけ作ってマスを未開放にした状態でカードを取得すると、自己修復される
- 事前推薦マスのブースへ訪問すると、そのマスが達成になり中央の空きが減らない
- カード外訪問が `cell_id = NULL` で記録され、`pending_rating` に含まれる

## 推薦エンジン側（`event-support-recommend`）

参考として記す。正本はそちらのリポジトリ。

- **単調性のプロパティテスト**（最重要）: 候補 A が候補 B をすべての条件属性で上回るなら、
  A の推薦順位は B 以上になる。**DRSA の理論そのものであり、破れていたら実装バグ**。
  ランダム入力を大量に生成して自動チェックできるため費用対効果が高い
- **教科書の標準例題によるゴールデンテスト**: 既知の入力で既知の規則が出る
- 同じ入力に対して同じ出力を返す（決定性）
- 決定表が0件・1件でも落ちず、フォールバックに落ちる
- 除外リストのブースが結果に絶対に含まれない
- 条件属性が欠損していても動作する
- 応答が必ず1秒以内に返る
- **`event-support-analytics` と特徴量の計算結果が一致する**（研究の生命線）
