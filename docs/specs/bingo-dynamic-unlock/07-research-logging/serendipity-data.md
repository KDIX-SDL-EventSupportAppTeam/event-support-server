# セレンディピティ分析のためのデータ要件

**今年のアプリでは、意図的なセレンディピティ戦略（推薦枠を「純粋推薦」と
「セレンディピティ狙い」に配分する）は実装しない。**
DRSA が素直に選んだ結果に不一致ジャンルが混ざるのは自然に起きるので、それを観測する。

**ただしデータは、大学院での研究に耐える形で取る。**
指標の定義は未確定であり、**後から何度でも再定義して計算し直せる状態にしておく**のが目的である。

## 暫定の定義（未確定）

> 事前アンケートで興味があると答えなかった分類のブースに実際に足を運び、
> 評価が高かった場合に、セレンディピティが高いとみなす。

この定義は変わる可能性がある。**だから指標を保存せず、生データを保存する。**

## 計算に必要なもの

| 必要なもの | どこに持つか | 状態 |
|---|---|---|
| その人が選んだ関心分野 | `user_survey_answers` | 事前アンケートの実装で確保 |
| ブースのカテゴリ | `booths.category_id` | あり |
| 推薦した候補**すべて**とスコア | `recommendation_scores` | 新規 |
| 推薦時の戦略・フェーズ | `card_unlock_events.phase` / `strategy` | 新規 |
| **推薦したが訪問されなかったもの**（分母） | `recommendation_scores.was_assigned` + `check_ins` | 新規 |
| 実際に訪問したか | `check_ins` | あり |
| 訪問後の評価 | `booth_ratings` | あり |
| **カード外訪問**（推薦なしの自発訪問） | `check_ins.cell_id IS NULL` | あり |

## 凍結して保存するもの（重要）

**カテゴリは運営が当日でも編集できる。** 後から再計算すると、推薦時点とは違う判定になる。
以下は**推薦した瞬間の値をそのまま保存する。**

- `recommendation_scores.interest_match` — 関心分野との一致（`MATCH` / `PARTIAL` / `MISMATCH` / `UNKNOWN`）
- `recommendation_scores.attributes` — 条件属性の値（JSON）
- `card_unlock_events.decision_table_size` — その時点の決定表の件数
- `card_unlock_events.global_checkin_count` — その時点の累計チェックイン数

## 分析でできるようになること

```
セレンディピティ率 =
    不一致カテゴリで推薦され、訪問し、高評価だった件数
  ÷ 不一致カテゴリで推薦された件数

比較対象:
  (a) 一致カテゴリで推薦された場合の同じ率
  (b) 自発訪問（推薦なし・カード外訪問）で不一致カテゴリに行った場合の率
```

**(b) が最も重要である。** これがないと「推薦されたから行った」のか
「もともと行く人だった」のかを分離できず、セレンディピティを起こしたという主張が成立しない。
カード外訪問のログがそのまま対照群になる（[D-16](../01-concept/decisions.md)）。

さらに以下も分析できる。

- フェーズ別（COVERAGE / SIMILARITY / DRSA）の踏破率・満足度の比較
  → **「データ量が増えると推薦が良くなる」の直接の証拠**
- 解放の回数別（1回目 / 2回目 / 3回目）の推薦精度の変化
- 推薦されなかった候補（`was_assigned = 0`）との比較
- 年代・性別による層別（条件属性に入れなくても、後から層別できる）

## 2軸の分離（研究発表上の要請）

打ち合わせで確認された通り、以下2つは**明確に分けて説明する必要がある**。

| 軸 | 測り方 |
|---|---|
| **レコメンド自体の効果** | 推薦されたマスへの訪問割合。去年（固定中央4マス）と今年（動的開放マス）を比較 |
| **周遊率向上の効果** | 訪問ブース数の分布（ヒストグラム）が去年と比べて右にシフトしたか |

「段階的目標を立てたから」なのか「レコメンドの精度が上がったから」なのかを混同しない。
**周辺マスを隠す設計自体も、レコメンドの見せ方の工夫の一部**として位置づける。

## 分析側との整合

指標の計算は `event-support-analytics` が行う。
**特徴量（条件属性）の計算コードは `event-support-recommender` の1モジュールに置き、
分析側はそれを import する**（コピーしない）。
「分析で使った定義と本番の推薦が違う」という事故を構造で防ぐ
（[ADR 0004](../../../decisions/adrs/0004-split-recommender-repository.md)）。
