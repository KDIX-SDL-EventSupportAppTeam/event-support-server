# エッジケース一覧

**実装時に必ず処理すること。**テストで固定するのが望ましい。

| # | ケース | 挙動 |
|---|---|---|
| E1 | 同一ブースへの再チェックイン | `UNIQUE (user_id, booth_id)` で弾き、`ALREADY_VISITED`（409）を返す。**エラー扱いにしない。**INSERT 前に SELECT で確認する（プロキシは重複キーを 500 に潰す） |
| E2 | 解放処理中に4件目のチェックインが来る | カード行の条件付き UPDATE で直列化する（[D-7](../01-concept/decisions.md)）。解放を取れなかった側は、解放完了後の状態を読み直して外側マスに反映する |
| E3 | 参加ボーナスのブースに実際に訪問した | `check_ins` には記録する（**評価も取る**）。既に `ACHIEVED` なので新たなマスは埋まらず、`cell_id` は既存のボーナスマスを指す。結果としてそのユーザーは解放までにボーナス以外の3件が必要になる（[D-11](../01-concept/decisions.md)） |
| E4 | 推薦サービスがタイムアウト・エラー | [フォールバック割当](../05-recommender/fallback.md)で**必ず解放する** |
| E5 | 出展ブースが当日中止 | `booths.is_active = 0` にして割当候補から除外。既に割当済みのマスは[運営 API](../06-api/admin-api.md) で差し替える |
| E6 | 事前アンケート未回答のまま来場 | **カードは必ず正常に生成される。**参加ボーナスのブース決定は既定実装のフォールバック規則に従う（[signup.md](../03-card-lifecycle/signup.md)）。`pickSignupBonusBooth()` は例外を投げてはならない |
| E7 | 中央の残り3件を埋めきる前に帰った | **何もしない。**外側は `LOCKED` のまま終わる。**これは正常な状態である。**去年の実測では滞在30分未満が37%。この状態で終わる参加者は相当数出る。**異常系として扱わないこと** |
| E8 | 同一ユーザーが複数端末でログイン | カードは `UNIQUE (event_id, user_id)`。同じカードが返る |
| E9 | クールタイム中の連打 | 429 + `cooldown_remaining_sec`。フロントはボタンを無効化する |
| E10 | タイムゾーン | DB は UTC。表示・集計で JST(+9) 変換。`src/lib/datetime.ts` を使う |
| E11 | 運営・出展者アカウント | `users.role <> 'participant'` を推薦の学習データと集計から除外する |
| E12 | オフラインキューのまとめ送信 | 複数件が同時に届く。クールタイムは `checked_in_at` の差でも判定する（[cooldown.md](../03-card-lifecycle/cooldown.md)）。3件目で解放が起きた場合、レスポンスの `unlocked: true` は**その1件にだけ**立つ |
| E13 | 有効ブース数が12件に満たない | 埋められるだけ埋め、残りは `state='EMPTY'`, `booth_id=NULL` にする。`LOCKED` のまま放置しない（[unlock.md](../03-card-lifecycle/unlock.md)） |
| E14 | 解放処理が途中で失敗し `UNLOCKED` なのに `LOCKED` マスが残る | `GET /bingo/card` が検知してその場でフォールバック修復する（self-healing） |
| E15 | 推薦結果に重複・存在しない・無効なブースが含まれる | サーバー側で除去し、不足分をフォールバックで補う。**推薦サービスを信用しない** |
