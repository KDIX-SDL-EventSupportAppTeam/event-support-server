# クールタイム

## 仕様

- 同一ユーザーの直前チェックインから **既定 0 秒**（＝無効）以内の新規チェックインを拒否する
- 環境変数 `CHECKIN_COOLDOWN_SEC` で変更可能（`src/config.ts` の `envSchema` に `z.coerce.number().int().min(0).default(0)` で追加）
- **`CHECKIN_COOLDOWN_SEC = 0` のときは判定自体をスキップする。** DB へ問い合わせに行かないこと
- 抵触時は **HTTP 429**、`result: 'COOLDOWN'`、`cooldown_remaining_sec` に残り秒数（切り上げ）を返す

## 判定

```sql
SELECT checked_in_at FROM check_ins
WHERE user_id=? AND event_id=? ORDER BY checked_in_at DESC LIMIT 1
```

**判定にはクライアントが送ってきた `checked_in_at` ではなく、サーバーの現在時刻との差を使う。**
`checked_in_at` はクライアント由来の値であり、端末時刻のずれや送信遅延で過去時刻が入りうる。

## なぜ既定を 0 にするのか

**クールタイムが本来防いでいた「同一ブースへの連続チェックイン」は、既に `check_ins` の
`UNIQUE (user_id, booth_id)` で構造的に不可能である。** 残るのは「異なるブースを短時間で
連続してスキャンする」ケースだが、これは正当な行動でもありうる（隣接ブースを続けて回る）。

一方でクールタイムには実害の実績がある。去年は 金180秒 / 土60秒で運用し、180秒は
チェックイン間隔中央値（金5.6分）の下限として効いて**行動データを歪めていた**（飽和24.2%）。
本機能は行動ログを推薦の判断材料に使うため、データを歪める要因は既定で外しておく。

**機構自体は実装しておき、既定値を 0 にする。** 本番で問題が起きたら環境変数だけで有効化できる。

値を変えると解放到達時間（3件 × 間隔）が変わる。**本番当日に安易に変更しないこと。**
変更する場合は運営と合意した上で環境変数で行う。
