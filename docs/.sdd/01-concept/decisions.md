# 設計判断と、既存コードに合わせるための確定事項

D-1〜D-5 は企画側の判断。D-6〜D-11 は**既存コードベースと突き合わせて本仕様書で確定させた**判断であり、企画書原文と異なる箇所を含む。**実装は本ファイルを正とする。**

---

## D-1 ゼロデータで16マスを決めることを諦める

推薦は初回ログイン時の一発勝負であり、カード生成後にマスの中身は変わらない（変わるのはタップ時の理由文だけ）。参加者の37%は全体データも薄い時間帯に来る（[background.md](background.md) 3）。

→ **問題を解消せず先送りする。** 3件の訪問と評価が入った後なら12マスを決められる。「解けない問題を解く」のではなく「解ける状態になるまで待つ」。

## D-2 解放条件は実訪問3件（2件ではない）

| 理由 | 内容 |
|---|---|
| 1件目は使えない | 初回訪問は飲食に集中し選好を反映しない。解放2件→有効データ1件、3件→**2件**。実質2倍 |
| **DRSA は比較を要求する**（最重要） | 核は優越関係＝「AよりBが良い」の順序比較。評価1件では比較対象が存在せず、その人の基準すら判定できない。**0組から1組への変化は、1組から2組への変化よりはるかに大きい**。ユーザー内平均でのセンタリングも1件では必ず0になり無意味 |
| 名義属性の多数決 | ジャンルタグは順序がなく多数決しか使えない。2件では割れたら判定不能（6〜7割が判定不能と推定）、3件なら 2対1 で必ず多数派が決まる |

**所要時間の検証:** チェックイン間隔中央値 3.4分（60秒クールタイム運用時の実態値）× 3件 = 10〜15分。滞在30分未満層（37%）でも届く。4件だと20分近くかかり、この層の半数が到達前に帰る計算だった。

## D-3 中央4マスの1マスは参加ボーナスとして最初から達成済みで配る

「イベントに参加してくれたこと」への報酬。中央4マス = **参加ボーナス1 + 実訪問3**。

- 「中央が埋まったら解放」という単純なルールを保ったまま、実訪問コストを4件から3件に削減
- 4ビンゴに必要な最小マス数が 11 → 実質 10 に下がる
- 中央2x2 = position 5,6,9,10 は**全10ライン中6ラインに乗っている**。ボーナスの置き場所として最適

**★ 中央2x2 自体は行でも列でも対角でもない。4マス揃ってもビンゴは1本も成立しない。よって中央完成時にコインは配らない。**報酬は「外側12マスの解放」そのものとする。

## D-4 解放後のカード外訪問がビンゴに寄与しない問題は許容する

外側12マスが確定した瞬間から、カードにないブースへの訪問はビンゴに寄与しない。12マスがセレンディピティ寄りなら、行きたいブースとビンゴが進むブースが乖離し作業感が出るリスクもある。

→ ビンゴゲームという制約がある以上やむを得ない。**既知のトレードオフとして記録し、エンジニア判断で許容する。**
→ ただしカード外訪問も**ログとしては必ず記録する**（`cell_id = NULL`）。学習データ・研究データとして必要。

## D-5 クールタイムは60秒

去年は 金180秒 / 土60秒。180秒は間隔中央値の下限として効いておりデータを歪めていた（飽和24.2%）。今年は60秒。**環境変数 `CHECKIN_COOLDOWN_SEC` で変更可能にする。**

---
以下、既存コードベースとの整合のために本仕様書で確定させた判断。

## D-6 主キーは CHAR(36) UUID（企画書の BIGINT AUTO_INCREMENT は採用しない）

既存スキーマは `organizers` / `events` / `booths` / `users` / `check_ins` / `booth_ratings` すべて `CHAR(36) PRIMARY KEY` の UUID であり、アプリ側で `randomUUID()` を採番している。新規テーブルだけ BIGINT にすると FK と採番方式が二系統になる。

→ **新規テーブルもすべて `CHAR(36)` UUID とし、`randomUUID()` で採番する。**

## D-7 解放の排他は `SELECT ... FOR UPDATE` ではなく条件付き UPDATE で行う（重要）

**本番の DB アクセスはさくら上のラッパー API への HTTP プロキシ経由であり（`src/db/http-proxy.ts`）、1リクエスト＝1 SQL で接続が維持されない。トランザクションも行ロックも使えない。** `beginTransaction` は `pool.ts` 側にしか存在せず、プロキシ実装は持っていない。

→ 冪等性は**条件付き UPDATE の `affectedRows` で判定する**。

```sql
UPDATE bingo_cards SET status='UNLOCKED', unlocked_at=?, updated_at=?
WHERE id=? AND status='CENTER_ONLY'
```

`affectedRows = 1` を取れたリクエストだけが解放処理の権利を持つ。0 なら既に他のリクエストが解放済みなので**何もせずカードの現状を返す**。中央マスの後出し割当も同じ形（`WHERE id=? AND state='EMPTY'`）で直列化する。詳細は [03-card-lifecycle/unlock.md](../03-card-lifecycle/unlock.md)。

**あわせて、INSERT 前に SELECT で重複を確認すること。**プロキシは重複キーエラーを 500 に潰すため `ER_DUP_ENTRY` を受け取れない（[ADR 0001](../../adrs/0001-sakura-proxy-error-masking.md)、既存の `checkins.ts` も同じ形）。

## D-8 事前アンケートは既存の `survey_questions` / `user_survey_answers` を使う

企画書 4.5 の `pre_survey_responses` は新規テーブルとして書かれているが、**既存に同等のテーブルが存在し、`user_survey_answers` には `UNIQUE (user_id, event_id)` が入っている**（2026-08-17 の作業指示で追加済み）。新規テーブルは作らない。設問構造は未確定なので、既存の回答保存形式をそのまま使う。

## D-9 評価は3段階を既定とし、段階数を環境変数で切り替える

企画書 10.1 は未決定だが、実装を止めないため既定値を置く。既存 `booth_ratings.rating` には `CHECK (rating BETWEEN 1 AND 5)` が付いており、3段階に切り替えると意味がずれるため**この CHECK は外し、アプリ側で `1..RATING_SCALE` を検証する**（MySQL 5.7 では CHECK は無視されるが 8.0 のローカル環境では効く）。

- `RATING_SCALE`（既定 `3`）
- 記録時に `booth_ratings.scale` として**その時点の段階数を保存する**。途中で設定を変えても分析側で正規化できるようにするため
- 判断材料: ブース関係者が目の前にいる状況では1〜2が押されず実質4と5の2値になる。また評価が付くのは約364件しかなく、5段階だとグレードあたりが枯れる

## D-10 「未評価の最新チェックイン」を評価対象として返す

企画書 5.3 は「前のブースの評価を聞く」とあるが、直前1件に限定すると**スキップした評価を永久に取り逃す**。

→ `pending_rating` は「そのユーザーの、まだ `booth_ratings` が無いチェックインのうち `checked_in_at` が最新のもの」を返す。今まさに作成したチェックイン自身は除く。

## D-11 参加ボーナスのブースに訪問しても中央マスは埋まらない（＝解放には別の3件が必要）

ボーナスマスは配布時点で `ACHIEVED` であり、そのブースに実際にチェックインしても新たなマスは埋まらない（[08-edge-cases](../08-edge-cases/edge-cases.md) E3）。つまりボーナスブースを訪問した参加者は、解放までに**ボーナス以外の3件**を回る必要がある。

これは仕様として受け入れる。ただし発生確率を下げるため、**ボーナスブースの選定では去年の訪問者数上位ブース（飲食・制作チーム系）を避ける**方針を既定実装に入れる（[09-open-questions](../09-open-questions/open-questions.md) Q-4）。

## D-12 カード外訪問でも評価は同じように求める

ビンゴには寄与しないが、推薦アルゴリズムの学習データとして必要。評価収集の分岐にカード内外の条件を入れないこと。
