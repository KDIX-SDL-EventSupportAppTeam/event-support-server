# ADR 0004: 推薦エンジンを別リポジトリへ切り出す

- **状態:** 採用
- **日付:** 2026-08-24

## 背景

ビンゴの動的段階解放にともない、推薦（ラフ集合／DRSA）の呼び出しが
1回から最大3回へ増え、フェーズによる戦略切替も入る。
推薦ロジックをどこに置くかを決める必要がある。

## 判断

**`event-support-recommender` として別リポジトリ・別サービスに切り出す。**
`event-support-server` からは HTTP で呼び出す。

## 理由

分割が妥当かどうかの基準3つが、いずれも該当する。

| 基準 | 該当 |
|---|---|
| 実装言語が違うか | Python（推薦） / TypeScript（サーバー） |
| デプロイ単位が別か | 推薦は状態を持たないので複数インスタンス化できる。サーバーは socket.io のため1インスタンス固定 |
| インターフェースが既に定義されているか | `POST /recommend/cells` の契約が仕様書にある |

加えて:

- **分析（`event-support-analytics`）と同じ言語**であり、特徴量の計算コードを共有できる。
  「分析で使った定義と本番の推薦が違う」という研究上まずい事故を構造で防げる
- 大学院での研究にそのまま持っていける独立資産になる
- 推薦が落ちてもアプリ本体は動く（タイムアウト＋フォールバック）。**障害が隔離される**

## 結果

- 契約の正本は `event-support-server/docs/specs/bingo-dynamic-unlock/05-recommender/contract.md`。
  推薦リポジトリ側は**リンクで参照し、内容をコピーしない**
- 特徴量の計算は推薦リポジトリの1モジュールにまとめ、
  **`event-support-analytics` はそれを import する**（コピーしない）
- `RECOMMENDER_URL` 未設定でもサーバーはフォールバックで正常に動く

## 却下した案

| 案 | 却下の理由 |
|---|---|
| サーバー内に TypeScript で実装 | ラフ集合の実装が困難。分析側とコードを共有できない |
| `event-support-analytics` に同居させる | 分析はバッチ、推薦はオンライン。デプロイとスケールの要件が違う |
