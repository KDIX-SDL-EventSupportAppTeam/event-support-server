# ADR 0005 — 推薦エンジンがフェーズ判定とアルゴリズム選択を担う

**日付:** 2026-05-13  
**ステータス:** 採用

## 背景

設計書（system-server.md §4.3・§7）は推薦アルゴリズムを差し替え可能にすることを要件としているが、誰がアルゴリズムを選択するかは明示されていなかった。候補として以下の2案を検討した。

- **案A:** Fastify がフェーズを判定し、使用するアルゴリズム名を推薦エンジンに渡す。
- **案B:** 推薦エンジンが自律的にフェーズを判定し、内部でアルゴリズムを切り替える。

## 決定

**案B** を採用する。推薦エンジンがチェックインデータを参照してフェーズを判定し、Strategy パターンでアルゴリズムを選択する。Fastify は `user_id` と `event_id` だけを渡す。

## 理由

- アルゴリズムの実装・フェーズ判定ロジックは推薦エンジン（Python + FastAPI）に集約することで、Fastify 側に推薦の詳細が漏れない。
- フェーズ判定に必要なデータ（チェックイン数・分布等）は推薦エンジンが直接参照する方が自然である。
- アルゴリズムを追加・変更する際に Fastify の変更が不要になる。

## アルゴリズムの段階

| フェーズ | 判定条件 | アルゴリズム |
|---------|---------|------------|
| 0（初期） | デフォルト | ランダム（実装の足場） |
| 1（序盤） | チェックインデータが少ない | コンテンツベース |
| 2（中盤） | データが蓄積 | ラフ集合 + MAB |
| 3（終盤） | データが豊富 | MAB + セッションベース |

## 影響

- 推薦エンジン（`recommender/`）内部に `PhaseDetector` と `RecommendationStrategy` インターフェースを定義する。
- 初期実装は `RandomStrategy` のみ。フェーズ判定ロジックは後から追加する。
- Fastify の推薦呼び出しは `POST /recommend { user_id, event_id }` のシンプルなインターフェースで固定される。
