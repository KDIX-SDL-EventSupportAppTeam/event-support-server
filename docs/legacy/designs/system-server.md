# システム・サーバー設計

クライアントを含む**全体システム構成**、バックエンド（Node / Fastify）、推薦マイクロサービス（Python）、DB・外部連携までの方針と、ドメインイベント・チェックイン・推薦ロジックのサーバー側の考え方をまとめた文書です。

**フロントエンドの画面構成・ディレクトリ・コンポーネント設計は [frontend.md](./frontend.md) に分離しています。** 本ファイルは「フロントのアーキテクチャ」ではありません。

**関連:** [設計インデックス](./README.md) · [DB設計](./database.md) · [API設計](./api.md) · [フロントエンド](./frontend.md) · [レビュー観点](./open-questions.md)

## 1. このアプリが何をするか

### 1.1 対象イベントとユースケース

出展者が複数のブースを設置し、参加者が自由に回るタイプのイベント（展示会・カンファレンス等）を対象とする。規模感は以下を想定している。

- 参加者：200〜500人
- ブース数：数十〜百程度
- 開催期間：1〜2日

このアプリは参加者がどのブースを回るかを**システムが推薦・誘導**し、参加者が自分から行かなかったようなブースにも足を運べる「新しい出会い」を提供することをコアバリューとしている。

### 1.2 登場人物（アクター）

| アクター | 役割 |
|---------|------|
| 参加者 | アプリを使ってブースを回る主役 |
| 出展者 | ブース情報を事前に登録する |
| 運営 | イベントを管理し、リアルタイムで状況を把握する |
| システム | データを分析し、参加者に次のブースを推薦する |

## 2. ユーザーの行動フローとデータの流れ

### 2.1 イベント前（準備フェーズ）

```
出展者
  → Googleフォームにブース情報を入力
      （ブース名・説明・カテゴリ・タグ等）
  → Google Apps Scriptがフォーム送信・編集を検知
  → バックエンドAPIを自動で叩く
  → DBにブース情報が登録・更新される

運営
  → 管理画面でカテゴリを定義
  → 管理画面でイベント固有のアンケート設問を設定
  → ブースごとのQRコード・手動コードをアプリが自動生成
  → 運営がQRコードを印刷してブースに設置
```

### 2.2 イベント当日（参加者フロー）

```
参加者がアプリにアクセス
  → ログイン（Googleログイン or メアド＋パスワード）
  → 初回アンケート回答
      - 固定設問：年齢層・職業・業種など属性情報
      - イベント固有設問：興味・関心など運営が設定したもの
  → ホーム画面へ

ブースを訪問
  → QRコードをスキャン or 手動コード入力でチェックイン
  → 評価モーダルが表示される（5段階評価・スキップ可）
  → サーバーにチェックイン・評価を送信
  → 推薦エンジンが次のブース候補（3択）を生成
  → WebSocketで参加者に即時プッシュ
  → 参加者が次のブースを選んで移動
  → これを繰り返す
```

### 2.3 イベント中（運営フロー）

```
運営ダッシュボード（WebSocketでリアルタイム更新）
  → どのブースに何人来たかを確認
  → 属性ごとの動きを確認
  → 会場の人の流れ・混雑状況を把握して会場運営に活用
```

## 3. 発生するイベントの一覧

| イベント名 | 発生タイミング | リアルタイム性 | 送信先 |
|-----------|--------------|--------------|--------|
| `user.registered` | 参加者がログイン・アンケート完了 | 不要 | DB保存のみ |
| `booth.checkin` | QRスキャンまたは手動コード入力 | **最優先** | DB + 推薦エンジン + ダッシュボード |
| `booth.rated` | チェックイン後の評価送信 | 不要 | DB保存のみ |
| `recommendation.updated` | チェックイン後に推薦が生成された | **最優先** | 該当参加者のクライアント |
| `booth.info.synced` | Googleフォームから情報が同期された | 不要 | DB保存のみ |
| `dashboard.stats.updated` | チェックインのたびに集計更新 | 高（数秒以内） | 運営ダッシュボード |
| `booth.label.updated` | ブース特性ラベルの更新 | 低（数分以内で可） | 全参加者クライアント |

## 4. アーキテクチャ

### 4.1 全体構成図

```
[参加者・運営のブラウザ（React PWA）]
        ↕ HTTPS REST API    （通常のデータ取得・送信）
        ↕ WebSocket         （リアルタイム推薦・ダッシュボード更新）
        ↕ Service Worker    （オフラインキュー・自動リトライ）
[バックエンド: Node.js + Fastify]
        ↕ HTTP（内部通信）
[推薦エンジン: Python + FastAPI]
        ↕
[MySQL（InnoDB）]
        ↑
[Google Apps Script] ← [Googleフォーム（出展者入力）]
```

### 4.2 フロントエンドとバックエンドの分離

フロントエンド（React）とバックエンド（Fastify）は完全に分離したプロジェクトとして管理する。

**理由：**
- 推薦アルゴリズムが複雑化してもバックエンドのみ改修すれば良い
- フロントをモバイルアプリ化する場合もバックエンドをそのまま使い回せる
- 責任の分離により保守性が高い

**デメリットと対策：**
- ローカル開発時は複数サーバーの同時起動が必要 → docker-composeで解決
- CORS設定が必要 → 開発・本番環境ごとに環境変数で管理

### 4.3 推薦エンジンをマイクロサービスとして分離

推薦アルゴリズムはFastifyとは別にPython + FastAPIのサービスとして独立させる。

**理由：**
- MAB・ラフ集合・セッションベース推薦など、実装したいアルゴリズムはPythonライブラリが充実している
- アルゴリズムの切り替え・追加・検証をバックエンド本体に影響を与えずに行える
- 検証段階・実用段階ともにアルゴリズムの切り替えが必要なため、差し替え可能な設計が必須

**切り替えの仕組み：**

推薦エンジンがフェーズを自動判定し、使用するアルゴリズムを内部で選択する（Strategy パターン）。Fastify はアルゴリズムを指定せず、`user_id` と `event_id` だけを渡す。

```
POST /recommend
{
  "user_id": "xxx",
  "event_id": "yyy"
}
```

推薦エンジン内部のフェーズ判定ロジックが、チェックインデータの蓄積量を見てアルゴリズムを選択する。初期実装はランダムアルゴリズムから始め、データが蓄積するにつれてコンテンツベース → MAB の順に自動移行する。

| フェーズ | 判定条件 | 使用アルゴリズム |
|---------|---------|---------------|
| 初期（開発・フェーズ0） | デフォルト | ランダム |
| フェーズ1（序盤） | チェックインデータが少ない | コンテンツベースフィルタリング |
| フェーズ2（中盤） | データが蓄積してきた | ラフ集合 + MAB |
| フェーズ3（終盤） | データが豊富 | MAB本格稼働 + セッションベース推薦 |

**内部通信のレイテンシについて：**

バックエンド → 推薦エンジン間の内部HTTP通信は5〜30ms程度。推薦結果はバックグラウンドで先読みキャッシュする設計（前のチェックイン完了時点で次の推薦を計算・保存）により、参加者が体感するレイテンシはほぼゼロになる。

## 5. 各技術の選定理由

### バックエンド：Node.js + Fastify

| 観点 | 理由 |
|------|------|
| 同時接続 | 非同期I/Oモデルで200〜500同時接続を効率よく処理できる |
| WebSocket | socket.ioとの統合がスムーズ、REST APIと1サーバーで統一できる |
| 開発速度 | TypeScriptとの相性が良く、型安全な開発ができる |

### 推薦エンジン：Python + FastAPI

| 観点 | 理由 |
|------|------|
| アルゴリズム | MAB・ラフ集合・セッションベース推薦等のライブラリが充実 |
| 拡張性 | アルゴリズムをモジュールとして差し替え可能な設計にしやすい |
| 将来性 | アルゴリズム研究者が参加する場合もPythonの方が扱いやすい |

### データベース：MySQL（InnoDB）

| 観点 | 理由 |
|------|------|
| 運用・インフラ | ホスティング・チームスキルに合わせて MySQL を採用（詳細は [ADR 0003](../adrs/0003-mysql-over-postgresql.md)） |
| 可変データ | イベント固有のアンケート回答・推薦ログの可変部分を `JSON` カラムで保持する |
| 信頼性 | InnoDB のトランザクションでチェックイン等の整合性を担保する |
| スキーマ | タグ等は配列型が無いため子テーブル（`booth_tags`）と JSON で表現する（[database.md](./database.md)） |

### リアルタイム通信：WebSocket（socket.io）

| 観点 | 理由 |
|------|------|
| 推薦の即時反映 | チェックイン後の推薦結果を参加者に即時プッシュできる |
| WiFi耐性 | 接続断時の自動再接続機能があり、不安定な会場でも安定して動作する |
| ダッシュボード | 同じWebSocket接続で運営ダッシュボードのリアルタイム更新も賄える |

### オフラインキュー：PWA（Service Worker）

| 観点 | 理由 |
|------|------|
| チェックイン失敗対策 | QRスキャン成功時点でクライアント側に一時保存し、通信失敗時も「チェックイン済み」として見せる |
| 自動リトライ | WiFi回復後に自動でサーバーに送信。ユーザーの操作は不要 |
| リスク | ブラウザを閉じる前に送信完了するよう画面上で案内することで対処 |

### Googleフォーム連携：Google Apps Script

| 観点 | 理由 |
|------|------|
| 出展者の操作性 | 出展者はGoogleフォームに入力するだけでよく、特別なツールが不要 |
| 自動同期 | フォーム送信・編集のたびにApps ScriptがバックエンドAPIを叩き、DBを自動更新する |
| コスト | 無料で動作し、追加インフラが不要 |

### デプロイ先

| サービス | 用途 |
|---------|------|
| Vercel | フロントエンド（React） |
| Railway | バックエンド（Fastify）+ 推薦エンジン（FastAPI）+ MySQL |

## 6. チェックイン周りの詳細フロー

### チェックイン方法
- **メイン：QRコードスキャン**（アプリ内カメラ）
- **フォールバック：手動コード入力**（ブースに掲示された6桁のコード）

### オフライン時の挙動
```
1. QRスキャン成功
2. Service Workerがチェックイン情報をローカルに保存
3. 画面上は即座に「チェックイン済み」と表示（UX担保）
4. 評価モーダルを表示（5段階評価・スキップ可）
5. バックグラウンドでサーバーに送信を試みる
6. 失敗した場合は一定間隔でリトライ
7. 成功したらsynced_atを記録
8. 長時間失敗が続く場合のみユーザーに通知
```

## 7. 推薦エンジンの設計方針

### フェーズ別アルゴリズム

推薦エンジンが自律的にフェーズを判定し、アルゴリズムを切り替える（詳細は §4.3 を参照）。

| フェーズ | 条件 | 使用手法 |
|---------|------|---------|
| フェーズ0（初期・開発） | デフォルト | ランダム（実装の足場） |
| フェーズ1（序盤） | チェックインデータが少ない | コンテンツベースフィルタリング + Warm-Starting Contextual Bandits |
| フェーズ2（中盤） | データが蓄積してきた | ラフ集合理論によるルール抽出 + MAB |
| フェーズ3（終盤） | データが豊富 | MAB本格稼働 + セッションベース推薦 |

### 推薦の3択構成

| 枠 | 内容 |
|----|------|
| 推薦枠 | 参加者の属性・行動履歴・評価に基づくパーソナライズ推薦 |
| 準推薦枠 | 属性はやや外れるが関連性がある準推薦 |
| ディスカバリー枠 | 属性スコアは低いが他参加者の評価が高い「意外なブース」 |

### 推薦スコアの計算方針

```
推薦スコア =
  ユーザー属性との一致度 × α
  + 過去の高評価ブースとの類似度 × β
  + MABの探索スコア × γ

ディスカバリー枠はスコアに関係なく固定で1枠確保する
```

## 8. ブース特性パラメータ

| パラメータ | 算出方法 |
|-----------|---------|
| 直近10分・30分のチェックイン数 | 時間窓でのチェックインカウント |
| チェックイン数の時間変化率 | 前の時間窓との差分 |
| 平均推定滞在時間 | 次チェックインまでの時間差で近似 |
| 訪問者の属性エントロピー | 訪問者の属性分布の多様性 |

```
🔥 急上昇中       → 直近チェックイン数が急増している
💎 じっくり系     → 推定滞在時間が長い
🎲 意外な人気     → 自分と異なる属性の人が多く訪問している
👥 幅広い支持     → 属性エントロピーが高い
```
