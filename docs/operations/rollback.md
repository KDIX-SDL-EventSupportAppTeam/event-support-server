# ロールバック手順（当日の「戻す・止める」）

当日のトラブル対応は、コードを直して `main` にマージするのではなく、**戻す・止めるだけで凌ぐ**。
デプロイの逆操作（Cloud Run のトラフィック切替、Firebase Hosting のリリース履歴からのロールバック）と、
機能の一時停止（推薦の切り離し・ガチャの停止・アプリ公開ゲートを閉じる）で対応する。
**推薦エンジンが落ちても、解放は自動選択に切り替わるだけでアプリは止まらない。**
DB の復元は最終手段であり、研究データを失う操作である。

## 0. 判断基準（最初に読む・運営向け）

| 症状 | 判断 | 理由・参照 |
|---|---|---|
| 参加者全員がチェックインできない（「エラーが発生しました」） | まず [run-day-guide.md](run-day-guide.md) §5（プロキシ）を試す → 直らなければ**server を戻す**（1-1） | データが入らない＝当日の記録が止まる |
| 推薦エンジンが落ちた／遅い／質が悪い | **戻さない・触らない**（[run-day-guide.md](run-day-guide.md) §4）。ダッシュボードのフォールバック率が上がるだけ | 解放は自動選択（フォールバック）で成立し続ける。慌てて触るほうが危険 |
| ビンゴのマスが開かない／解放演出が出ない（複数人） | エンジニアに連絡 → 直前デプロイが原因なら**server を戻す**（1-1） | 解放は研究の中核データ |
| 景品切れ・ガチャの誤動作 | **ガチャだけ止める**（3-2） | 他機能に影響しない |
| 参加者向け画面が真っ白・崩れる（複数人） | **frontend を戻す**（1-3） | server は無関係のことが多い |
| 事故で誤ったデータが大量に入った・スキーマが壊れた | **最終手段。先生の判断で DB を戻す**（2）。必ず 2-1 を先に行う | 研究データを失う操作。判断権者は §4 |

## 1. アプリケーションを戻す（エンジニア）

### 1-1. server（Cloud Run）を前のリビジョンに戻す

**コンソール（推奨）**:

1. Cloud Run → サービス `event-support-server`（リージョン `asia-northeast1`）を開く。
2. 「リビジョン」タブで 1 つ前のリビジョンを選び、「…」→「トラフィックを管理」。
3. 100% をそのリビジョンへ割り当てて保存する。

**CLI（コンソールが使えないときの補助）**:

```bash
gcloud run revisions list --service=event-support-server --region=asia-northeast1 --format='table(name,active,creationTimestamp)'
gcloud run services update-traffic event-support-server --region=asia-northeast1 --to-revisions=<1つ前のリビジョン名>=100
```

**注意**:

- リビジョンには環境変数も含まれる。3-1 で `RECOMMENDER_URL` を外した後にこの操作で古いリビジョンへ戻すと、`RECOMMENDER_URL` が付いた状態に戻ってしまう。戻した後は 3-1 の状態を見直す。
- `--max-instances=1`・セッションアフィニティ・タイムアウトの設定はリビジョン側に保存されており、戻し先のリビジョンでも保たれる。`min-instances` はサービス側の設定であり、トラフィック切替では変わらない。
- 備考: デプロイ設定は `min-instances=0` だが、当日はコンソール等で 1 へ引き上げる運用にする前提（別の文書では 1 を必須と書いており、値が揃っていない）。引き上げの実施者・タイミングは確認中（未確定・要判断）。

**確認**:

- `curl -s https://<server の URL>/health` が `{"ok":true}` を返す。
- 運営ダッシュボードの数字が更新される。
- 参加者 1 名が実際にチェックインできる。

### 1-2. recommend（Cloud Run）を前のリビジョンに戻す

server と同じ操作をサービス `event-support-recommend` に対して行う。

```bash
gcloud run revisions list --service=event-support-recommend --region=asia-northeast1 --format='table(name,active,creationTimestamp)'
gcloud run services update-traffic event-support-recommend --region=asia-northeast1 --to-revisions=<1つ前のリビジョン名>=100
```

戻す判断の前に、recommend リポジトリの `docs/OPERATIONS.md` §0（「壊れてもアプリを止めない」設計）を読む。多くの場合は 3-1 の「切り離し」で足り、recommend 自体を戻す必要はない。手順の詳細は recommend リポジトリの `docs/OPERATIONS.md` §4・§6 を参照する（当日の運用チェックリストは同リポジトリの管轄）。

### 1-3. frontend（Firebase Hosting）を前のリリースに戻す

Firebase コンソール → プロジェクト `event-support-app` → Hosting → 「リリース履歴」→ 1 つ前のリリースの「…」→「ロールバック」。

**確認**: シークレットウィンドウで参加者用 URL を開き、ホームが表示されることを確認する。

frontend の静的ビルドには API の URL がビルド時に焼き込まれているため、server を戻したときに合わせて frontend も戻す必要は通常ない。

## 2. DB を戻す（最終手段・先生）

**先に §0 の判断基準を確認すること。DB の復元は研究データを失う操作であり、最終手段としてのみ行う。**

### 2-1. DB を戻す前に「現在の状態」をダンプする（必須）

phpMyAdmin の「エクスポート」→ 対象 DB の**全テーブル・構造とデータ**→ SQL 形式で書き出す。ファイル名に `after-incident-YYYYMMDD-HHMM` のように現在時刻を含めて保存する。

**これを取らずに次の 2-2 へ進まない。** 理由: 流し戻すと「復元に使うダンプの時刻〜今」までの当日データ（チェックイン・評価・解放・コイン使用）が消える。ここで取っておけば、消えたデータを後で分析側が突合できる。

### 2-2. 流し戻す

[production-db-apply.md](production-db-apply.md) §4 の手順のとおり、phpMyAdmin の「インポート」で復元する。復元に使うのは**本番スキーマ適用前に取ってあるダンプ**（production-db-apply.md §1）であり、2-1 で新たに取ったダンプではない。

**テーブルを丸ごと作り直す方式のスクリプトを、当日の復旧手段として使わない。** 理由は production-db-apply.md に書いたとおり、既存データを消して一から作り直す性質のものであり、当日データを取り直せないイベントの選択肢には無い。

### 2-3. 失われるもの・所要時間

「復元に使うダンプの時刻〜現在」までのすべての当日データ（チェックイン・評価・解放・コイン使用）が失われる。2-1 で取った現在のダンプは、失われたデータを後で分析側が突合するために残す。

所要時間: **未計測**（リハーサル T-2 で実測し、この欄を更新する）。

## 3. 部分的に止める

### 3-1. 推薦エンジンだけ切り離す

```bash
gcloud run services update event-support-server --region=asia-northeast1 --remove-env-vars=RECOMMENDER_URL
```

- これを実行すると推薦の呼び出しが行われなくなり、解放は自動選択（フォールバック）に切り替わって成立する。参加者から見て機能は止まらない。
- 戻すとき: `--update-env-vars=RECOMMENDER_URL=<推薦の URL>`。
- どちらの操作も新しいリビジョンを作るだけで、コードは変わらない。

### 3-2. ガチャだけ止める

操作手順は重複させず、[run-day-guide.md](run-day-guide.md) §1（設定変更）・§3（景品切れ時の全停止）を参照する。運営ポータルに専用の画面がない場合の代替手段（curl 等）は未確定（三上くんに確認中）。

### 3-3. アプリ公開ゲートを閉じる（全参加者を待機画面へ）

```bash
curl -X PUT "https://<server の URL>/api/v1/organizer/events/<event_id>/app-access" \
  -H "Authorization: Bearer <organizer の JWT>" -H "content-type: application/json" \
  -d '{"mode":"closed"}'
```

- `mode` だけを送れば、公開開始・終了・事前アンケート締切の日時は既存の値のまま変わらない。
- 再開するときは `{"mode":"open"}` を送る。
- 操作は監査ログに 1 件残る。
- 運営ポータルに同じ操作をする画面があるかどうかは未確認（三上くんに確認中）。画面が無ければこの curl 手順のみで運用する。
