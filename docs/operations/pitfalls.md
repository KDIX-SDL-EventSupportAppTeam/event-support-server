# 運用の落とし穴

## デプロイ

| 落とし穴 | 何が起きたか | 対策 |
|---|---|---|
| `--set-env-vars` は全置換 | コンソールで手追加した `RECOMMENDER_URL` が CD で消え、ビンゴ解放が無言でフォールバックになった（2026-10-12） | 環境変数は必ず `cloudbuild.yaml` に書く。デプロイ後に env の差分と `GET /api/v1/admin/events/:event_id/recommender/state` を確認する |
| フロントとサーバーの世代ずれ | 旧リビジョンのサーバー × 新フロントで評価 API が 422 を返し続けた（2026-09-28・2026-10-06） | 実機テストの前に `GET /health` の `commit` と、フロントの `<meta name="app-commit">` が想定どおりか確かめる |
| フロントの index.html キャッシュ | デプロイ後もしばらく旧バンドルが配信される | 確認時は `?v=<任意>` を付けて開く |
| 運営ログインの event_id はビルド時固定 | 削除済みイベントの ID のままビルドされ、運営がログインできなくなる | イベントを作り直したらフロントを再ビルドする（フロントの `docs/reference/development.md`） |
| Cloud Run を複数インスタンスにする | socket.io の配信が届かない運営画面が出る | `max-instances=1` を維持（[ADR 0002](../decisions/adrs/0002-cloud-run-single-instance-for-websocket.md)） |

## DB（さくらプロキシ）

| 落とし穴 | 何が起きたか | 対策 |
|---|---|---|
| エラーが全部 500 に見える | 一意制約違反も 500 になり、原因が区別できない | INSERT の前に SELECT で重複を確認する（[ADR 0001](../decisions/adrs/0001-sakura-proxy-error-masking.md)） |
| 時刻列の JST / UTC 混在 | DB 既定値で入る列は JST、アプリが書く列は UTC | イベント後の分析では列ごとにタイムゾーンを補正する |
| 高負荷時の周期的な 500/502 | 負荷試験で毎分 430 件を超えると約 31 秒周期で失敗した（想定負荷では問題なし） | 当日の想定（ピークで毎分 25 件前後）を大きく超える一斉操作を運営が仕掛けない |
| 数値が文字列で返る | 集計値が文字列のまま届く | 数値を返す式には数値列名か `COUNT/SUM/AVG/EXISTS` の別名を付ける（`src/db/type-coerce.ts`） |

## イベントの切り替え

本番イベントを新しく作るときは、推薦側の対象イベント ID・カテゴリ設定・フロントの再ビルドをまとめて行う。
手順は [run-day-guide.md](run-day-guide.md) と推薦リポジトリの運用文書を参照。

## データの扱い

- 本番 DB のダンプ・トークン・キー・個人を含むファイルは**リポジトリにコミットしない**。ドキュメントにも値を書かない
- 検証には架空データを使う
