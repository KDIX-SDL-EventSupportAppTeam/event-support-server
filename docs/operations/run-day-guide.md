## 1. ガチャの設定を変える（運営ができる）

ガチャの「1ライン何枚」「上限何枚」「おまけ何枚」「有効/無効」は、
**運営ポータルの「ガチャ設定」画面から、その場で変更できる**（デプロイ不要）。

| 項目 | 意味 | 使いどころ |
|---|---|---|
| `is_enabled`（有効/無効） | オフにすると全員のガチャが止まる（`403 GACHA_DISABLED`） | 景品切れ・トラブル時の**全体停止** |
| `coins_per_line`（1ラインあたりの枚数） | ビンゴ1ラインで何枚もらえるか（0〜10） | 「もらえる枚数が多すぎ/少なすぎ」の調整 |
| `max_coins`（上限） | 1人が持てる最大枚数（0〜50） | 景品数に対して配りすぎているとき絞る |
| `bonus_coins`（おまけ） | 全員に一律で足す枚数（0〜10） | 後述の**誤使用の救済**、開始記念の配布など |

操作の反映は即時。参加者はアプリを再読み込みすると新しい枚数になる。

### 変更してよい範囲の注意

- **`max_coins` を下げても、すでに使ったコインは戻らない。**
  「使った数 > もらえる数」になった人は、残り 0 枚として扱われる（マイナスにはならない）。
- 迷ったら **`coins_per_line` と `max_coins` は当日いじらない**。
  `bonus_coins` と `is_enabled` の2つだけで当日の運用はまわる。

## 2. 誤使用の救済 —— 台帳から行を消さない

参加者が誤ってコインを使ってしまった、二重に引かれた、などの申し出があったとき:

> **その人の分の `bonus_coins` を +1 する（＝おまけを1枚増やす）。**
> ガチャの使用履歴（台帳）から行は**絶対に消さない。**

理由: 使用履歴は研究データそのもの。1行でも消すと「いつ・何枚使われたか」の集計が
狂い、**当日のデータが壊れる**。取り消しは仕様として存在しない。

> ⚠️ `bonus_coins` はイベント全体に一律で効く。特定の1人だけに +1 する仕組みは無い。
> 個別救済が必要な場合は、その場で景品を手渡しし、システム上はいじらないほうが安全。
> 「全体に配ってよい」と判断できるときだけ `bonus_coins` を上げる。

> ⚠️ 参加者向け Q&A は「コインは**最大4枚**」と案内している（frontend の固定文言・§8）。
> `bonus_coins` を上げると手持ちが 4 枚を超え、**アプリの案内と食い違う**。
> 上げるなら、掲示・アナウンスでも「今回はおまけを配っています」と伝える。

## 3. 景品切れ

**景品が尽きたら `is_enabled` を `0`（無効）にして、ガチャ全体を止める。**

- 景品ごとの在庫管理はシステムでは**していない**。止めるのは全体単位。
- 止めるとアプリは「準備中」表示になり、コインは減らない。
- 補充できたら `is_enabled` を `1` に戻す。

## 4. 推薦エンジンが落ちたとき

**症状**（運営ダッシュボード）:

- 「推薦エンジンの状態」が「取得不能」と出る（`UNREACHABLE` などの表示）
- 「直近30分のフォールバック率」がじわじわ上がる（例: 数 % → 数十 %）

**対処: 何もしなくてよい。**

- **解放（ビンゴのマスが開くこと）は成功し続ける。**
  推薦が使えないときは「訪問者数の少ないブースから自動で選ぶ」方式に切り替わるだけ。
  参加者から見て止まらない。
- 記録上は `FALLBACK_COVERAGE` という印がつく（後で分析側が区別できる）。
- **推薦のパラメータ（しきい値など）を当日その場で触らない**（推薦側 ADR 0009）。
  触ると挙動が読めなくなり、復旧の切り分けができなくなる。
- エンジンが復帰すれば自動で元に戻る。運営操作は不要。

**「取得不能」と「設定ミス」は画面で区別できる**:

| 画面の表示 | 意味 | 当日やること |
|---|---|---|
| `UNCONFIGURED` | そもそも推薦エンジンとつないでいない | 想定どおり。放置 |
| `UNAUTHORIZED` | 合言葉（トークン）の不一致。こちら側の設定ミス | エンジニアに連絡（急がない。解放は動いている） |
| `UNREACHABLE` | エンジンが落ちている／ネットワーク | 様子見。復帰を待つ |
| `BAD_RESPONSE` | エンジンの応答の形が想定と違う | エンジニアに連絡 |

## 5. さくらプロキシ（本番DBの通り道）が落ちたとき

サーバーは本番DBに「さくらプロキシ」というHTTPの中継を通してつながっている。
ここが落ちると **アプリ全体が反応しなくなる**（チェックインもカードも保存できない）。

**症状**:

- チェックインしても「エラーが発生しました」が返る（特定の人だけでなく全員）
- 運営ダッシュボードの数字がまったく更新されない

**対処**:

1. まず**アプリの再読み込みを1回試す**（一時的な詰まりなら直る）。
2. 直らなければ**エンジニアに即連絡**。運営側でできる復旧操作は無い。
3. 復旧までの間、参加者には「あとでもう一度チェックインしてください」と案内する。
   チェックインは**同じQRを何度読んでも1回しか数えない**ので、後追いで問題ない。
4. コインの使用も**同じ操作を繰り返しても二重に減らない**作りになっている。
   「引けたか分からない」人には、もう一度引いてもらってよい。

## 6. ダッシュボードの数字の読み方

| 数字 | 見方 | 落ちていたら疑うこと |
|---|---|---|
| **評価回収率**（`rating_collection_rate`） | チェックインのうち、感想評価まで書いてくれた割合。**最重要**。推薦の質がここで決まる | 下がったら: 評価モーダルが出ていない／閉じられている。スタッフが「チェックインのあと星をつけてね」と声かけ |
| チェックイン数 / 評価数 | 参加者の活動量。時間帯の山が想定どおりか | 想定より極端に少ない → プロキシ詰まり（§5）を疑う |
| 解放の到達人数（1回目/2回目/3回目） | 何人が段階を進めたか。3回目が極端に少ない → 途中離脱が多い | 会場導線・ブース数を疑う。システム異常ではないことが多い |
| 直近30分のフォールバック率 | 推薦エンジンが使えず自動選択に切り替わった割合 | 高い → 推薦エンジンが落ちている（§4）。**解放自体は成功しているので慌てない** |
| 推薦エンジンの状態 | エンジンとの疎通。`UNREACHABLE` 等 | §4 の表を参照 |

**評価回収率が落ちたときが最優先。** 他の数字は多少ぶれても当日の体験は壊れない。

## 8. スケジュール・Q&A はアプリでは変更できない

参加者画面の「タイムスケジュール」「Q&A」はアプリに固定で入っている（frontend ADR 0005）。
**当日タイムテーブルが変わっても、アプリの表示は変えられない**（変えるには再デプロイが要り、当日は行わない）。
変更は会場の掲示・アナウンスで伝える。アプリ側にも「掲示・アナウンスをご覧ください」と書いてある。
