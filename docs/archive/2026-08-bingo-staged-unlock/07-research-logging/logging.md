# 研究データの確保

**このアプリは研究のためのものである。**当日取り逃したデータは二度と取れない。以下は機能要件ではなく**研究要件**であり、P2 だが省略不可。

## 1. `cell_assignment_logs.global_checkin_count`（最重要）

**割当を行った時点でのイベント全体の累計チェックイン件数**を必ず記録する。

```sql
SELECT COUNT(*) FROM check_ins ci
JOIN users u ON u.id = ci.user_id
WHERE ci.event_id = ? AND u.role = 'participant'
```

これは「**データ量が推薦精度を規定するか**」という本研究の中心的な問いを検証する変数である。去年は 11:00 台にログインした参加者が累計CI 約20件の状態でカードを受け取っており、その推薦が機能していたかを事後に検証できなかった。

- 解放処理・フォールバック・self-healing・運営差し替え、**割当が起きる全経路で記録する**
- 12マス分を1回の複数行 INSERT でまとめて書く（性能要件のため）
- `strategy` は VARCHAR。将来の実験デザイン（[Q-5](../09-open-questions/open-questions.md)）で `PURE` / `SERENDIPITY` / `RANDOM` を出し分けても**スキーマを壊さない**

## 2. カード外訪問（`check_ins.cell_id IS NULL`）

解放後、カードに載っていないブースへの訪問はビンゴに寄与しない。**それでも必ず記録する。**

- 推薦アルゴリズムの学習データとして必要
- 「12マスがセレンディピティ寄りすぎて参加者の行きたい先と乖離した」ことを事後に測る唯一の手がかりである（[D-4](../01-concept/decisions.md)）
- **評価も同じように求める**（[D-12](../01-concept/decisions.md)）

## 3. `visit_order`

そのユーザーの何件目の訪問か（1始まり）。**1件目は選好情報として使えない**（飲食に集中する）という去年の知見を今年も検証・利用するために必要。推薦の条件属性としても使う想定。

## 4. スタッフ除外

去年は運営疑いアカウント（34ブース訪問）が未除外のまま分析され、集計を歪めていた。

**`users.role <> 'participant'` を、以下の全てで除外する。**

- フォールバックの訪問者数集計
- `global_checkin_count`
- 運営ダッシュボードの指標
- 推薦サービスへ渡す全体データ

新規カラムは追加しない。既存の `users.role` で足りる。

## 5. タイムゾーン

**DB は UTC 保存。表示・集計時に JST(+9) に変換する。**去年の分析でここが罠だった。既存の `src/lib/datetime.ts`（`isoToMysqlUtc` / `utcMysqlNow`）を必ず使い、`NOW()` を SQL に直書きしない。

## 6. 分析側との接続

`event-support-analytics` が本番後にこれらのテーブルを読む。**カラム名を分析側と揃えること**（`event-support-analytics/docs/.sdd/` を参照）。特に `strategy` の値の集合は分析コードの分岐に直結するので、増やす場合は分析側にも反映する。
